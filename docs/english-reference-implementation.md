# English Reference Implementation

English (`fa-en-us`) is the reference implementation for Nova while new-language generation is paused. The goal is to prove the complete app-facing path before the same contract is promoted to the remaining languages.

## Architecture boundary

Nova now has three distinct layers:

1. **Canonical content** — concepts, lexemes, word forms, utterances, dialogues, grammar, exercises and audio metadata in normalized MySQL tables.
2. **Lesson delivery** — `lesson_steps` plus step-member tables define the exact learner-facing sequence. A canonical item may be reused by multiple steps without duplication (for example an utterance can appear in both `phrases` and `repeat`).
3. **Frontend read model** — the lesson API joins canonical content, delivery steps, localized text, audio and lexical annotations into one versioned payload.

The frontend must consume the delivery graph. It must not group raw content by `lesson_key` or recreate the lesson sequence itself.

## Database order for a fresh database

The database is still empty, so build it from the current schema and migrations before importing any content.

Apply:

```text
database/schema.sql
database/migrations/001_curriculum.sql
database/migrations/002_multilingual_core.sql
database/migrations/003_lesson_item_lexemes.sql
database/migrations/004_level_import_audio.sql
database/migrations/005_writing_exercises.sql
database/migrations/006_lexical_annotations.sql
database/migrations/007_lesson_delivery.sql
```

Then apply the shared seeds/course definitions and all English curriculum seeds for Pre-A1 through C2.

## One English reference importer

Use the reference entrypoint instead of running the legacy English level entrypoints one by one:

```bash
python database/import/en/reference.py --dry-run --require-approved
python database/import/en/reference.py --require-approved
```

Before touching MySQL, the reference chain runs `scripts/validate_english_reference_flow.py`. That source-level contract test covers all English production batches and rejects unresolved step references, orphan learner-facing content, duplicate exercise delivery, missing intro/review boundaries and semantic stage regressions.

The reference importer then runs, in order:

1. the app-wide English dictionary;
2. Pre-A1 through C2 canonical content;
3. deterministic delivery-step materialization for every lesson;
4. English lexical span annotations after all source rows exist.

The reference level importer currently installs `scripts/english_lexical_identity_patch.py` before canonical materialization. This makes lexeme and word-form UUIDs use the same batch-independent identity contract as the app dictionary without changing the paused non-English import pipelines. After the frontend contract is proven, this identity logic should be promoted into the shared materializer and the compatibility adapter removed.

Generated audio files are not regenerated by this process. Import the existing English `*_audio.sql` metadata after canonical content. The API first resolves audio by canonical entity ID and then falls back to `source_text_hash`, which keeps the current generated audio compatible while lexical identity is being standardized.

## Dictionary and concept semantics

The app dictionary is broader than lesson target vocabulary. Dictionary-created concepts are therefore fallback senses rather than lesson context.

- dictionary meanings live in localized `concept_terms`;
- `concepts.definition` is not populated with Persian text, keeping the canonical concept row language-neutral;
- dictionary `concept_lexemes` links use `relation_type='related'`;
- lesson-authored semantic links use `primary`, so a lesson-specific meaning wins when a vocabulary card needs one context while explicit tap annotations can still point directly to the dictionary concept.

This avoids choosing an arbitrary dictionary sense when one lexeme participates in multiple concepts.

## Lesson delivery model

`database/migrations/007_lesson_delivery.sql` adds:

- `lesson_steps`
- `lesson_step_items`
- `lesson_step_exercises`
- `dialogue_turn_translations`

The deterministic builder is `scripts/lesson_flow.py`. The materializer is `scripts/materialize_lesson_delivery.py`.

The stored stage sequence is strictly monotonic:

```text
context -> understand -> learn -> speak -> practice -> conversation -> review
```

The builder raises if a future change creates a stage regression. That makes the ordered payload safe for a frontend progress/stage rail without special handling.

Typical concrete steps are:

```text
intro
dialogue_preview
exercise (comprehension)
vocabulary
phrases
grammar
repeat
exercise (speaking)
exercise (practice)
roleplay
dialogue_challenge
review
```

### Canonical vocabulary delivery

`vocabulary` is intentionally not equivalent to the old `concepts` UI bucket.

- an explicit `lexeme` is delivered as the canonical dictionary unit;
- an explicit `word_form` is delivered as its own canonical morphology-aware item;
- a `concept` with a learner-facing form is used as a compatibility fallback only when no explicit lexeme represents that concept in the lesson.

This prevents the frontend from flattening lexemes and inflected forms back into duplicate concept strings.

Steps are semantic records, not UI components. `label_key` exists for localization; presentation copy stays out of the canonical flow builder.

## Lesson API

Run the dependency-free reference server with the same MySQL environment variables used by the importers:

```bash
python -m api.server --host 127.0.0.1 --port 8787
```

Endpoints:

```text
GET  /api/v1/health
GET  /api/v1/courses/{course}/levels/{level}/lessons
GET  /api/v1/lessons/{lesson_slug}?course=fa-en-us
POST /api/v1/exercises/{exercise_uuid}/grade
```

The lesson response contract is versioned with `schema_version: 1`. Its JSON Schema is `api/lesson-payload.schema.json`.

A lesson payload has this shape (abbreviated):

```json
{
  "schema_version": 1,
  "lesson": {"id": "...", "slug": "a1-calendar-01", "title": "..."},
  "course": {
    "slug": "fa-en-us",
    "learner": {"language": "fa", "variant": "fa-IR"},
    "target": {"language": "en", "variant": "en-US"}
  },
  "path": {"cefr": "A1", "unit": {"slug": "a1-calendar", "title": "..."}},
  "steps": [
    {
      "key": "04-phrases",
      "stage": "learn",
      "type": "phrases",
      "items": [
        {
          "role": "useful_phrase",
          "content": {
            "kind": "utterance",
            "target": {
              "value": "What day is it today?",
              "annotations": [
                {"start": 0, "end": 4, "surface": "What", "entry": {"lemma": "what", "meaning": "چه"}}
              ],
              "audio": {"url": "..."}
            }
          }
        }
      ]
    }
  ]
}
```

## Lexical tap contract

Offsets in `lexical_annotations` are Unicode code-point offsets in `[start, end)` form. The API re-checks `source_text[start:end] == surface_text` on every read and drops stale annotations instead of sending broken ranges to the frontend.

Each annotation returns a compact app dictionary entry containing the available canonical IDs plus lemma, POS, pronunciation/transliteration, concrete word form/features and the learner-language meaning.

Exercise annotations are keyed by their JSON `source_path`. The lesson GET only exposes annotations for learner-visible prompt fields; answer/solution content stays behind grading.

## Exercise security boundary

`GET lesson` does **not** include canonical correct answers or `is_correct` option flags. The frontend posts the learner response to:

```text
POST /api/v1/exercises/{exercise_uuid}/grade
{"value": ...}
```

Automatic exercises return correctness and the solution after submission. Rubric-based writing returns the rubric/model response after submission and reports `gradable: false` for server-side exact grading.

## CI contract

`.github/workflows/content-validation.yml` now treats the reference architecture as release-critical. It compiles the API and delivery tooling, validates the complete English source graph, and dry-runs the single English reference importer in addition to the existing content/audio/educational checks.

A change to `api/**`, delivery tooling, importers, migrations, content or audio therefore cannot silently drift away from the reference contract.

## Frontend integration rules

The production frontend should:

- render `steps` in API order and never infer flow from raw item kinds;
- use `role` to choose a component variant, not to identify canonical content;
- render `vocabulary` generically from the returned content kind (`concept`, `lexeme`, or `word_form`);
- use lexical annotation offsets to create tappable spans;
- keep answer checking behind the grading endpoint;
- use payload audio URLs directly and not rebuild TTS paths;
- store progress against lesson/step IDs, while treating content IDs as reusable canonical entities.

## Promotion rule

English is the contract test. Once the production frontend consumes this payload successfully, the lexical identity adapter and delivery materialization can be promoted into the shared importer and then applied language by language. No new language content needs to be generated to complete that promotion.
